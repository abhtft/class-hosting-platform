# Changelog

For teachers who run their own copy. Each release lists what is new, what (if anything) you must do, and whether it is safe to apply without thinking. Updating is always: the release's own `upgrade` command (each GitHub Release shows it) (or, with a git clone, `git pull` then `node setup.mjs upgrade`; or ask the teacher MCP: "plan an update").

## 2.9.0 (not released yet)

- **Sign in with Google for the apps students build (steps A2 of docs/AUTH_PLAN.md).** The starter backends now carry a sign-in helper (`class_auth`, Python and Node) and the page has a sign-in bar (`AuthBar`, `useUser()`) and an example private route. A student turns it on with `npm run signin -- on` (it needs the backend on); the platform gives the app its own client in the one shared Cognito pool and its sign-in values. The app keeps its own signed session cookie (default 7 days, setting `auth.sessionDays`); the page never sees a token. On the student's computer a pretend visitor signs in at once. `npm run check` now warns about a login of your own (a password field, a token in browser storage, a `/login` or `/signup` route, password hashing or token making) and points to the platform's sign-in; the AI editor's rules say the same. The gateway now passes the visitor's cookies to the app, and the local dev servers send the cookies an answer sets. The Google return address to register is shown by `npm run signin` before anything exists. Guide: [docs/SIGN_IN.md](docs/SIGN_IN.md). **To apply:** the platform part is already live; the kit follows on the next deploy. The teacher must create a Google client once and store it as `/student-deploy/auth-google` before a student can turn sign-in on.

## 2.8.0

- **Sign-in for student apps, platform side (step A1 of docs/AUTH_PLAN.md).** One Amazon Cognito user pool for the whole platform, with one Google registration that the teacher sets up once. Each student app gets its own client with its own return address, and the app uses PKCE, so no client secret is stored. Turning an app's sign-in off removes only that app's client. The Google setting is read from Systems Manager (`/student-deploy/auth-google`) and is refused plainly when missing. **To apply:** nothing is live yet; the deploy role needs the Cognito and Systems Manager permissions, which come with the next plan (not shown yet).

## 2.7.0

- **Add the install-as-an-app feature to sites that were already built.** A new add-on, "Install as an app", copies the install files (a web app manifest, the install script and three default icons) into the site's public folder and adds six lines to its index.html. The student's AI editor adds it after a yes, with `add_addon`; the terminal does the same with `npm run addons -- add installable-app`. It never overwrites a file the student made: if a file of the same name exists and is different, nothing is changed. `remove_addon` puts the page back exactly as it was and removes the files it made (a file the student edited is kept). Nothing for a teacher to do; the add-on is in the kit's catalogue. Plan: docs/INSTALLABLE_PLAN.md (step I3).

## 2.6.0

- **The student's site can be installed like an app (no app store).** The starter site now has a web app manifest, three default icons (a 512 and 192 pixel icon and an iPhone icon), and a small install script (`public/install.js`). On Android, Chrome, Edge and computers an **Install app** button appears when the browser offers it; on iPhone and iPad a button shows the three Add to Home Screen steps. Nothing is cached, nothing is stored and no permission is asked. New projects get it by default; the install is always a tap by the visitor. Plan: docs/INSTALLABLE_PLAN.md. **To apply:** nothing for a teacher; students get the files with the next kit sync. Older projects can add it later (planned, step I3).

## 2.5.2

- **Student backend limits raised to what AWS allows.** The defaults were cautious choices of this platform, not AWS rules, so they now sit at (or just under) the real AWS ceilings: a request may run **27 seconds** (was 10, and 25 with the class AI; AWS's HTTP front door ends every request at 30 s and the platform keeps 2 s of margin for its gateway), a backend function gets **3,008 MB** of memory (was 256; this account's AWS cap, checked on the live account, and it can be raised with a quota request), and a backend may be **50 MB zipped and 250 MB unzipped** (was 5 and 50; AWS's function limits). The class AI wait is 27 s too. Unchanged on purpose: the number of requests a student may make, the in-flight limits, storage sizes (a stored value stays at 64 KB; DynamoDB allows up to 400 KB per item but the student helper and local dev server enforce 64 KB) and the 15-minute background jobs, which already sit at the AWS maximum. A backend that already exists gets the new memory and time on its next publish (the platform now brings an older function in line once its code update has finished; before, memory and time were only set when a function was first created). Higher memory and longer requests raise the cost of a busy backend (still bounded by each student's run allowance); lower them in `config/settings.json` (`backend.memoryMB`, `backend.timeoutSeconds`) if you prefer. Kit 2.5.2: the rules, the local dev server warning and `npm run check` use the new numbers. **To apply:** `plan`, then `apply <id>` (one environment variable changes), then `publish`; students get the kit by sync.

## 2.5.1

- **Set up a class project from the terminal: `npx -y <portal address> init`.** Until now a project could only be created by asking the AI editor ("set up my class project"), so `npm run login` failed in any folder that was not a project yet. Now, in an empty folder, `class-platform-mcp init [folder]` writes the same starter the editor tool writes, installs the site's packages (about 10 seconds), and offers `npm run login` right away (paste the token your teacher gave you); then `npm run dev` and `npm run deploy` work. `--no-install` and `--no-login` skip those steps. It refuses a folder that already has files and never overwrites anything. The editor tool `init_project` and the terminal command share one piece of code. `setup` now mentions the command. **To apply:** a platform update (`publish`), nothing else; no AWS change.

## 2.5.0

- **Every platform setting is in one place: `config/settings.json` (steps S0 and S1 of the settings plan).** About 170 limits, defaults and times (file sizes, requests at once, session length, AI and storage caps, retention, the Lambda sizes and throttles, the feature switches, the installation names) are described once, each with a plain explanation, default, range, scope (`runtime` or `deploy`) and risk. The platform functions no longer hold numbers of their own: they read them through one small module (`lambda/platform_settings.py`), and `docs/SETTINGS.md` is generated from the registry. **No behaviour changes**: every value is exactly what it was (137 constants were compared before and after), and the template's environment variables still win where a deployment sets them. Tests make sure the registry, the code, the CloudFormation template and the generated page agree, and fail if a new limit is written into a Lambda file instead of the registry. Changing a setting from the portal or a command (S2, S3) is the next step. **To apply:** nothing is needed to keep today's behaviour; the next `upgrade` carries the new files.

- **Add-ons: teacher-approved skills and open-source packages that the AI editor can add to a project.** A student says "make a dashboard with charts"; the AI looks at the catalogue (`list_addons`), asks "Add the Charts add-on?", and on a yes adds it. Six skills (frontend design, accessibility, responsive layout, charts and dashboards, forms, a portfolio page) put a guide in `skills/`; six modules (Pico CSS, Lucide icons, Recharts, Motion, the Inter font, a day picker) also add their package to `frontend/`. New command `npm run addons` (list, show, add, remove, verify), new editor tools `list_addons`, `add_addon`, `remove_addon`, a rules section for the AI, and the maintainer tool `node starter/addons/pin.mjs` for teachers who change the catalogue. ## 2.3.2

- **Alerts and a cost budget are part of the install.** The guided install now asks for an e-mail address and a monthly budget (default $10), stores the address, passes it to the stack so the error alarms exist, and creates an AWS Budget that e-mails at 80% and 100% of the amount and when 100% is forecast. Flags: `--alert-email`, `--budget`, `--no-alerts`. New command `alerts --email <address> [--budget <usd>]` for a platform that was installed without them (then `plan` and `apply` to add the alarms). `verify` shows a warning when either is missing, `destroy` removes the budget (and, with `--everything`, the stored address), and an update never clears an alert address the stack already has. AWS sends each address a confirmation e-mail that must be opened. **To apply:** `alerts --email <your address>`, then `plan` and `apply <plan id>`; nothing changes for students.

- **Backups now include class knowledge.** `export` and `import` (and `transfer`) copy the `knowledge/` folder: every student's books, the class library and their search indexes. Before this a restore or a move left the books behind. Students' stored data also gets **point-in-time recovery** (restore to any second of the last 35 days; a few cents at most), which needs an `apply`. Traces are not in a backup on purpose (they expire after 30 to 90 days; download an archive from the Traces tab to keep them), and the messages and documents now say so.

- **A class can use the AI together: the backend limits follow your AWS account.** The gateway let only 3 student requests run at once for the whole platform (right for a new AWS account, which allows only 10 concurrent function executions), so a class of 30 asking the AI in the same minute mostly saw "busy". The install and `plan` now read the account's Lambda concurrency limit and set the caps from it (the whole limit is used, ten executions stay free for the portal): a limit of 1000 allows about 247 requests at once, up to 8 per student, and about 494 requests a second. They are template parameters (`BackendInflightGlobal`, `BackendInflightPerStudent`, `BackendApiRate`, `BackendApiBurst`, `BackendWaitMs`); a new account keeps today's small values and the install tells you how to ask AWS for more. When every slot is busy, the gateway now **waits up to 1.5 seconds** for one to free up (only on accounts with room for it), and the starter's `api()` **asks again up to three times** on "busy" (the platform answers that before your code runs, so repeating is safe). `verify` shows a warning until the account can serve a class of 30. **To apply:** raise the limit once (AWS console, Service Quotas, AWS Lambda, Concurrent executions, request 1000: free, usually granted in a day), then `plan` and `apply <plan id>`; the kit sync brings the retry to student projects (kit 2.3.2). A measuring script for a real platform is `tests/live_load.py`.

- **Project sync: your source files on every computer, and team projects, without GitHub accounts.** Students now have `npm run push` and `npm run pull` (and `npm run project`). A student's project is kept in the platform's own bucket, so the same code is on a second computer after `npm run login` and `npm run pull`. The teacher can make **team projects** (the new **Projects** tab: choose members, open any file, see who changed what and when, put an earlier version of a file back, freeze, clean up old versions, delete). It is not Git: whole files move, and when two people changed the same file `push` stops and says who changed it, nothing is overwritten, and `pull` saves their copy as `<file>.theirs` (`push --mine` and `pull --theirs` are the two ways out; `--dry-run` shows a plan). Secrets, `node_modules`, build output, the kit's own files and the `knowledge/` books are never synced; a file can be 5 MB, a project 50 MB and 500 files. Files are stored by their SHA-256 and checked by S3 on upload and by the client on download; the portal never reads a file. Backups (`export`, `import`, `transfer`) include `projects/`. New: `lambda/projects.py`, routes under `/api/student/projects` and `/api/admin/projects`, one new bucket permission (`projects/*`, the portal function only), `tools/project.mjs` in the kit (kit 2.3.2). **Automatic saving:** each student is asked once (in the terminal after a deploy, or by the AI editor, which sees it in `status`); a yes copies the whole existing project to the platform and from then on every deploy saves it by itself (never stopping the deploy); a no is remembered; `npm run project -- --auto on|off` changes it. The editor tool server gets four tools, `project_status`, `push_project`, `pull_project` and `project_auto` (they ask before they act). Existing users and their existing work: see "Moving existing users and existing work onto project sync" in `docs/PROJECT_SYNC.md`. No setting to switch on; it costs cents of storage. Details: `docs/PROJECT_SYNC.md`. **To apply:** `plan` and `apply <plan id>` (one permission); the kit sync brings the commands to student projects.

## 2.3.1

- **Compute worker (optional, off by default): one small machine for heavy checks.** A new feature you ask for with `plan --enable worker` (it is not part of "install everything", because a machine costs money while it runs). It creates one EC2 machine (m7i-flex.large, 2 vCPUs and 8 GB, x86, 30 GB encrypted disk, us-east-1; a size a Free plan account may use, the ARM c7g sizes need a paid-plan account) that is **off** until you start it. A new **Worker** tab on the teacher page shows its state, the hours used this month with a cost estimate, a **Start now** button (the machine runs its checks, writes a report to S3 and shuts itself down), **Start and keep on** (stays on until the time limit, for you to look around through Systems Manager), **Stop now**, an optional **Run every day at [hour]** switch, the time limit, and the last report. A control function runs every 15 minutes as a **watchdog**: it stops a machine that has no start request or has run past its limit, so a hung job can never run for a month. Nothing can connect to the machine from the internet (no inbound rule, no key pair, IMDSv2 only), its role reaches only the `worker/` folder of the bucket, only the portal and the control function may start and stop that one machine, and no student code runs on it. The image is chosen once and kept, so a new Amazon Linux release never replaces the machine. The machine runs `worker/runner.py` from this repository at every start (published to the bucket by `portal-publish`): the first start installs the software the tasks need (git, Node.js with npm, Python 3.12 with pip, jq, compilers) and a marker file stops it from reinstalling. A **monthly cap on machine minutes** (default 40 hours, set on the Worker tab) refuses a start once it is reached. Students have no access to it and no student code runs on it (students who need more than a web request already have Background Jobs). This release builds the machine, the toggle, the schedule and the watchdog; the real tasks (daily quality probes, judging flagged answers) come later. See `docs/COMPUTE_WORKER_PLAN.md`. **To apply:** `plan --enable worker`, show the plan, `apply`; about $4 a month at 30 minutes a day (the machine only while it runs, the disk always).
- **Traces (first part): a step-by-step record of every answer.** A new optional feature, absent until you install it (`plan --enable traces`) and then recording only for students you have not switched off. The platform's own functions now write one small record per step of an answer: the class AI proxy records each model call (model, tokens, cost, time, how it ended) and the knowledge search records which passages were found and how well they matched. Steps of one answer are joined by a trace id (the AI proxy and the search return it in an `x-trace-id` header). **By default no text is stored** (only lengths, counts, scores, ids and costs); per student you can choose masked text (emails, phone numbers, Aadhaar and PAN-like numbers and keys replaced) or full text, a retention of 30, 60 or 90 days (default 90, every item expires by itself) and a daily limit. A new table with two small indexes (`TracesTable`, pay per use, nothing while idle), a narrow permission for the two writers (the `t#` prefix only) and read and delete for the portal. Teacher routes: `POST /api/admin/tokens/{id}/traces`, `GET /api/admin/traces`, `GET|DELETE /api/admin/traces/{slug}/{trace_id}`. Tracing never breaks or blocks an answer. **Helper steps (T2):** the student kit's `answer()` and agent runs now carry one trace id to the AI call and the book search and report their own steps (the answer, each tool call, the agent summary) once at the end through a new `POST /v1/trace` on the knowledge API; a run paused for approval continues the same trace. Results include `trace_id`, and the starter page shows it as a short "Reference" with a one-line notice that answers are recorded. Best effort: a trace problem never changes an answer. Kit version 2.3.0 (kit sync brings it). **Traces tab (T3):** a new Traces tab on the teacher page lists answers (newest first, filter by student or day, 'Older' for more); opening one shows every step with its details, copy as JSON, and delete. Each student's panel has a Traces card to switch recording on or off and choose how much is stored (numbers only, masked text, full text), how long it is kept (30, 60 or 90 days), what the student may see (stored for the coming student view) and the daily limit. **Student view (T4):** a student can see how their own app answered, only if the teacher allows it (per student: nothing, numbers only (default) or what is stored). New routes `GET /api/student/traces` and `/api/student/traces/{trace_id}` and, in the kit, `npm run traces` (list) and `npm run traces -- tr_...` (every step). Another app's trace is simply not found. **Archive, reminder and download (T7, first part):** the Traces tab shows a banner when the oldest traces will be deleted within 30 days, and "Download archive…" produces one compressed JSON-lines file for all students or one, for a date range, optionally only answers that searched one shelf (the file holds what was stored: text only for students whose setting stores text). Once a month, when traces are about to expire, the daily sweep sends one email through the existing alert email (nothing is sent without the alert email). New routes `GET /api/admin/traces/status` and `/export`; the daily sweeper may query the day index and publish to the alert topic. **Privacy hardening (T5):** at the numbers-only level no text can remain even when an app notes something under a key of its own (strings stay only under a short list of label keys such as model, tool, doc and section; keys that look like text, for example an email address, are dropped); the masked level now masks every string, not only the text keys, and recognises more Indian identifiers (IFSC, GSTIN, passport, UPI id, Devanagari digits, long account numbers) and IP addresses; one trace holds at most 200 steps; an app's reported steps have a daily budget (20 per allowed trace); and the teacher can delete all traces of a student at once (their Traces card). **Daily summaries and alerts (T6):** every night the platform writes the numbers of the day before (answers, how many said the books do not say, answers with an error, tokens, cost, model time; for the class and for each student) as small items kept 400 days, from the trace summaries only (no extra cost to speak of). The Traces tab shows the last 14 days in a small table (today live). With the alert email set up, you get one email a day at most when the share of "the books do not say" is 15 points above the previous week's (at least 20 answers), or when 20% of answers had an error. New route `GET /api/admin/traces/summary`; the nightly sweeper may write and read its own `r#` items. Not built yet: replay of stored questions with new settings, a file for Phoenix, and the student page panel, the student view, reminders and download (see `docs/TRACEABILITY_PLAN.md`, steps T2 to T7). Format and privacy rules: `docs/TRACE_SCHEMA.md`. **To apply:** `plan --enable traces`, show the plan, `apply`, then publish; nothing changes for students until the teacher uses the settings.

## 2.2.0

- **Class knowledge: books a student's app can answer from.** A new optional feature, off for every student until you switch it on, and absent from your platform until you install it (`plan --enable knowledge`). The teacher gives a student a book shelf: PDFs and text files are read once and a student's app asks a question and gets the passages that answer it, with book, page and section, and a flag that says when the books do **not** answer ("The books do not say." instead of a guess). You can also keep a **class library** that every student with the feature can search but not change. Search is plain Python over S3: no vector database, nothing runs while idle. Reading a textbook costs a few US cents once (the class AI's Google key does the embedding, or OpenRouter with the same model id); a class-wide monthly ceiling (default 3 dollars) stops new books while search keeps working; at most 2 books are read at once so a class uploading together cannot starve the portal. Two small functions with narrow permissions (listed in `docs/KNOWLEDGE_CONNECTOR.md`, guarded by a test). The student kit gets the `class_knowledge` helper (Python and Node, offline keyword search for text books in `npm run dev`), rules for AI editors (cite sources, never guess, book text is data not instructions), an interview question, and `status` lists Class knowledge. **To apply:** `plan --enable knowledge`, then `apply`; make sure the AI secret holds `GOOGLE_API_KEY`; switch the feature on for a student; kit sync brings the helper to existing projects. Needs the backend.

- **Books from a folder: `knowledge/` and `npm run knowledge`.** A student puts books in `knowledge/<shelf>/` and runs `npm run knowledge` (`npm run deploy` does it too, without waiting and without ever stopping the deploy): new files are uploaded and read, unchanged files are skipped by content hash, a changed file replaces the book of the same name once the new copy is ready, nothing is deleted unless `--prune`, `--dry-run` shows the plan, `status` the state of each book. It uses the student's login with the portal (new routes under `/api/student/knowledge`, same limits as the API; the shelf key never leaves the function; another student's shelf and the class library cannot be named). The kit git-ignores `knowledge/` (books are often copyrighted), `npm run check` warns if they are tracked anyway, and offline `npm run dev` searches the text books of the folder. **To apply:** a platform update (new portal routes, code only: no new AWS permissions), then the kit sync brings the tool to projects.

- **AI patterns for student apps: a safe agent helper, quality tools and a pattern guide.** No switch and no AWS change: they are kit files that every project receives by kit sync. `class_agent` (Python and Node) runs a small tool-using agent: the model proposes one JSON step at a time and the helper checks it before anything happens. It enforces budgets (steps, seconds and an estimate of tokens), refuses unknown tools, wrong arguments and repeated calls, cuts long tool results and hands them back as data the model is told never to obey, reports a failing tool as one short sentence (never a stack trace), stops with an honest message when a budget runs out, returns a trace of every step, and holds any tool marked `needs_approval` until a person says yes (the paused run is plain JSON a project can keep in class storage). `class_quality` gives an answer cache (the same question is answered once; for book answers the key includes the passages found, so a changed book is never served an old answer), thumbs feedback, a test runner for the app (`evaluate`: must contain, must not contain, must refuse, time limit, optional AI judge) and `evaluate_retrieval` (recall, MRR and refusal rate of the book search). `PATTERNS.md` in the kit says which pattern to use (plain call, answer from books, router, agent, background job, human approval, quality loop), with the smallest working version of each and a checklist; the rules for AI editors, the interview and the `deploy` feature check know about them. Works offline in `npm run dev`. Tested with scripted models in both languages (no AI spend), then on a real account with the live class AI (Gemini): an agent answered from the class books in two steps and stopped for approval before saving. That run found that listing tools as `name(arg: kind)` makes Gemini attempt a native function call, fail ("malformed function call") and return nothing, which broke most book-search goals; tools are now listed as the exact JSON line to send, with a note that the reply is plain text, and the same goals pass every time. The agent also retries once when the AI provider hiccups. A fuller run (search the books, then save a note after approval) found three more things, all fixed: the model read "[needs a human's approval first]" as "I may not use this tool" (it now says the program asks the person, so the tool is requested normally), it searched the same tool four times with slightly different words (a tool may now be used at most 3 times per run, configurable), and a run resumed after approval had already spent its step budget (each resume now starts a fresh budget). The starter backend gets working example routes in its own `study` file (`/study` with the answer cache, `/feedback`, `/agent`, `/agent/approve` keeping a waiting run in class storage), `evals/study.json` and `npm run eval` (runs a cases file against the running backend or a deployed site, exit code 1 when a case fails), and an agent can be tried offline in `npm run dev` with `mock=[...]`, a scripted reply list used only while the class AI is the offline mock. The starter page also gets the matching parts (`frontend/src/patterns.ts`, `StudyPanel.tsx`, `AgentPanel.tsx`): an answer with its sources and thumbs, and an agent panel whose approval card shows the exact text the agent wants to use, what it read to decide, and Approve and Decline buttons, with a readable trace of every step. Checked in a real browser (offline agent: nothing saved before Approve, saved after, nothing after Decline) and on the live site. One known gap: kit sync replaces managed kit files with what the portal publishes, so a project's copy of a helper newer than the portal is put back until the portal publishes the new kit.

## 2.1.2

- **Background jobs: work that takes longer than a web request.** A request stops after 10 seconds (25 with the class AI), so an AI pipeline, a report or a big import could not be built. With jobs switched on, the page starts a job (`runJob('report', input)` from `frontend/src/api.ts`, or `POST /api/_jobs/<name>`), the student's own function runs it for as long as the teacher allows (default 5 minutes, at most 15), and the page reads the result when it is done. **Off for every student until you switch it on** (the new **Background jobs** card under Backend in the student's panel) with three limits: jobs a day (20), at the same time (1) and minutes per job (5). How it works and what it costs: the same code is also deployed as a second function `sd-<name>_job` with the longer time limit (the web function keeps its 10 s), and a platform runner function waits for it and records the result. A finished job is kept one day. **A job never shows a visitor the student's own error text** (it may hold a secret): the page sees a plain message, and `npm run logs` shows the details (job lines are marked `[job]`). A 40-second test job on real AWS cost about two hundredths of a cent. The platform runs at most 2 jobs at once in total (a new AWS account may allow only 10 concurrent Lambda executions). The student kit has an example job in both backends, the page helper, local support in `npm run dev`, the rules for AI editors and an interview question. The `status` command and the AI editor's feature check list Background jobs. **To apply:** `upgrade` (a new runner function and a role; nothing existing is replaced), then switch jobs on for a student and have them publish the backend once more. Found by running it on a real account: the job list first used a table scan that the gateway's role (rightly) cannot do; it now reads single items, with a test that keeps it that way.

- **Student sites now send basic security headers.** Pages and `/api/*` answers on `<student>.<your domain>` now carry `X-Content-Type-Options: nosniff` (a file is never treated as a different type than it says), `Strict-Transport-Security` for one year on that host only (not its subdomains: your root domain may host other things) and `Referrer-Policy: strict-origin-when-cross-origin`. Until now student sites sent none (the portal always did). It deliberately sends **no frame restriction and no Content-Security-Policy**, so a student can still embed their site in a school page and load what their app needs; a header a student's own backend sets for HSTS or the referrer policy wins. Sites on a student's **own custom domain** (the separate multi-tenant distribution) do not get these headers yet. **To apply:** `upgrade` (a CloudFront update, a few minutes; sites stay up).

- **A new student's `npm install` no longer prints security warnings.** The starter's frontend used `vite` 5, which pulls an `esbuild` with a known weakness in its development server (1 high and 1 moderate in `npm audit`, printed to every student on their first install). The template now uses `vite` 7 and the matching React plugin: 0 vulnerabilities, the same site builds the same way (the sample site's size is unchanged), and the kit already requires Node 22, which these versions need. Only **new** projects get it: `frontend/` is the student's own folder, so existing projects are never touched. A student who wants it runs `npm install -D vite@7 @vitejs/plugin-react@5` in `frontend/`.

- **`verify` now audits every file your portal publishes, not only the kit.** The signed version file lists the sha256 of each published file (the portal pages, the student downloads, the kit zip and every editor package), and `verify` fetches each one from the live portal and compares, naming any that differ ("`student.html` (changed)", "`class-platform-mcp-2.1.1.tgz` (HTTP 404)"). Until now only the kit was covered, so a page or an editor package changed by someone who could write the portal's files (but cannot sign) would not have been noticed. A browser or `npx` cannot check a signature, so for these files the audit is the teacher's: `verify` after a publish, and now and then. No AWS change and no kit change: **To apply:** run `publish` (or `upgrade`), then `verify`. A platform published before this has no list and `verify` simply skips the check.

## 2.1.1

Found by running 2.1.0 on a real account with a real student.

- **The student kit now has its `.gitignore` when your portal publishes it.** `npm` never puts a file named `.gitignore` into a package, so the teacher package you run had no `.gitignore` to copy, and every kit your portal published (2.0.x and 2.1.0) lacked it. A new student's `npm run check` then failed, and `npm run login` inside a git folder refused to save the token ("`.env.local` is not ignored"), until someone created the file. The template now keeps it as `gitignore.txt` and the kit builder renames it, and a test fails if a file npm would drop is ever added to the template again. The check's hint now says what to put in the file (it used to say "restore it from the kit", which was impossible). **To apply:** `upgrade` publishes the new kit; a student who already has a project without `.gitignore` creates it (the check shows the lines) or copies it from a freshly downloaded kit.

- **Errors-only logs now show timeouts.** The current Python and Node runtimes write a timeout only as a `REPORT ... Status: timeout` line, not as "Task timed out", so `npm run logs --errors` and the portal's "Errors only" box hid the most common failure. They now look for `Status: timeout` and `Status: error` too, and the `INIT_START` lines at every cold start are dropped as noise. Needs `upgrade` (the platform's own function).

- **A "Bring online" button for a site you took offline.** A site taken offline came back only through Extend or a request approval, and the card then showed no way back. The Token card now has **Bring online**: it serves the archived files again and leaves the expiry as it is (an expired token must be extended, because the sweeper would archive the site again; a revoked one cannot be brought back). The API has `POST /api/admin/tokens/{id}/online`. Needs `upgrade`.

- **A leftover saved state can no longer plan to remove your features.** `plan`, `upgrade` and the feature switches started from a small file the tool keeps on your computer (`~/.class-platform-teacher/install.json`). That file is keyed only by the stack name, so a file left by another AWS account or profile (for example a test platform with every feature off) made the plan for your real platform say "remove the backend, AI and storage and the student data table". The guard that refuses to replace or remove data stopped it, so nothing was ever changed, but the plan was useless until you deleted the file by hand. Now, once an install is finished, the live stack is the truth: if its features or domain differ from the saved file, the plan uses the live stack and corrects the file. An install that is still in progress is left alone. No AWS change; takes effect when you run the new version's `plan` or `upgrade`.

## 2.1.0

- **A stale site can no longer stay stale for a year.** Published files told CloudFront to keep them for a year, relying on the publish to clear them. If that clearing ever failed (AWS throttling, or the custom domain's own cache), visitors kept seeing the old site with no sign of it, and a failure of the main clearing even failed the publish after the files were already live. Now the lifetime is one day at most (browsers still revalidate pages on every visit), a failed clearing never fails the publish, and the student's answer says plainly that the old version may show for a while and to publish again. Normal publishes behave exactly as before (cleared at once). Applies to files published after you run `upgrade`; a site is re-stamped the next time its student publishes.

- **A Usage tab on the teacher page.** One view of what the class is using: how many students have the backend and the class AI on, runs used against what is allowed, AI spent so far, **the most the AI can cost** (the caps added up, per day / month / total) and how many students are at 80% or more of an allowance, with each student's runs and spend meters, fullest first. It is built from the list the page already loads: no new request, no AWS change, no student content. Every costly feature is still off for every student until you switch it on, and each has its own cap.

- **The student's AI editor now interviews before it builds.** A new kit file `INTERVIEW.md` (and a short section in the rules) tells the assistant, for a new app or a big change, to ask at most two rounds of 3 to 6 plain questions with choices and a default (who it is for, the one thing a visitor does in 10 seconds, pages, what it remembers, what the AI does, the look, what it must not do, plus extra questions for a portfolio, shop without payments, event, quiz or game, notes, tracker, form, AI helper and presentation), to say early what the platform cannot do, and then to write a one-page `SPEC.md` and get a yes before coding. It never asks about technology and skips the interview when the student already gave a detailed description. The file follows your version like the rest of the kit. No AWS change.

- **Students (and their AI editor) can read the backend logs properly.** `npm run logs` and a new `logs` tool for the AI editor show what the published backend printed: the **newest** lines (the portal used to show the oldest 50 of the hour, so a fresh error could be missing), without the START/END noise, with the end of long messages kept (the real error is at the end of a traceback), and with the values of the student's own variables hidden as `***`. `--errors` shows only errors and tracebacks; `--minutes` looks back up to 3 hours. The portal's Backend card gets an "Errors only" box and a time choice. The kit rules tell the AI to read the logs first when the live backend fails. No permission change: students got the logs before, only the function code and the kit change (students receive the kit by themselves; teachers `upgrade` for the function code).

- **The student kit is now signed (2.1.0).** The platform creates an AWS KMS signing key (about $1 per month; no platform function can use it) and signs the kit's version file every time the portal is published. Students' projects pin the public key from their first signed kit and accept a later kit only if it is signed by that key and not older than the one they have (a rollback you publish carries a newer serial, so it still works). A refused kit never blocks a student: nothing is changed, they see why, and `npm run deploy` carries on with the kit they have. After a move to a new AWS account (a new key) a student runs `npm run trust` and confirms the new key. `verify` now checks the signature. **To apply:** `upgrade` (it creates the key and publishes the signed kit); students pin the key with their next deploy. Not covered yet: the editor package (`class-platform-mcp`) and the portal's web pages.

- **Security: the platform's functions can no longer write the kit or the portal pages.** The upload-handling function and the daily sweeper could write anywhere in the sites bucket, including `portal/`, where the student kit and the portal pages live. Since students' projects now sync the kit from there, a flaw in upload handling could have been turned into code running on students' computers. Both functions are now limited to `sites/`, `archive/` and `uploads/`, and the portal function may only **delete** (never read or write) a student's stored files under `userdata/`, which the teacher's "clear" needs. Only your own credentials (`portal-publish`) can publish `portal/`. A test fails if any function is granted the whole bucket or `portal/` again. **To apply:** `upgrade` (a permissions change only, nothing students see). Signing the kit so students' computers can tell a genuine kit even if the portal were tampered with is a separate step that is planned.

- **`destroy` now removes the students' backend functions too.** Students' backends (`sd-<name>` Lambda functions) are created at run time, not by the stack, so a destroy used to leave them and their log groups in the account. Now `destroy` finds the functions that use this platform's student sandbox role (never another platform's, never a function without the `sd-` name), deletes them and their log groups, and the preview counts them. `destroy --everything` also deletes the platform's own function log groups. A function that cannot be deleted is reported with the exact command, and the result is not "ok". Per-student OpenRouter keys are not revoked by AWS: after a destroy with class AI, revoke them in your OpenRouter dashboard (the message says so).
